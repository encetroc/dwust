Problem. The interaction interface requires callers to coordinate deployment, turn identity, legality, stat changes, and victory; small helpers do not hide that knowledge.

Solution. Concentrate authoritative combat decisions and mutations in a deep module, with input and preview crossing the same rules seam.

Evidence: combat_input checks range, AP, walkability, and line_clear; update_combat_visuals repeats those checks, while its blue range tint checks only AP and distance. Victory is checked both inside casting and in finish_if_won. Existing spell_tests exercise helpers, not a full cast or turn progression. These are observed differences, not claims that every tint is intended to mean “legal target.”

Deletion test: deleting a duplicate eligibility block in favor of one authoritative decision concentrates knowledge; merely moving each helper to another file would just move complexity. Keep the useful pathfinding and damage implementation.

Adapter discipline: input and preview are existing consumers, not justification for swappable rules adapters; keep the rules concrete until two real implementations exist.

  • Depth: fewer caller invariants
  • Locality: one legality decision
  • Leverage: input and preview agree
  • Tests cross the rules interface

Test leverage: verify deployment restrictions, rejected casts without AP loss, accepted AOE casts, occupied movement with MP deduction, turn-budget reset, and victory through the same seam used in play.

Problem. HUD interaction reads a Window directly while world and combat read GameViewport; click-consumption knowledge leaks into world movement but not combat.

Solution. Deepen HUD interaction around the existing viewport seam, and make same-frame pointer ownership coherent before either world or combat handles a click.

Evidence: set_destination consults HudState; combat_input never does. HUD dragging and context menus read PrimaryWindow, so they receive no cursor in the windowless capture. HudPlugin chains its own systems, but their ordering relative to world and combat input is not explicit. The close-click test manually sets suppress_world_click instead of running the close interaction.

Deletion test: remove duplicated Window cursor reads and caller-specific suppression handling, concentrating the decision in HUD interaction; deleting HudState without replacing ownership would merely scatter the same checks.

Adapter discipline: window input and scripted windowless input already exist: two adapters justify this seam. No new general input framework is needed.

  • Depth: pointer ownership hidden
  • Locality: consumption precedes gameplay
  • Leverage: both game modes benefit
  • Tests use both input adapters

Test leverage: drive drag, close, and menu dismissal through actual schedules; assert the same click neither moves the world player nor moves or casts in combat, including with no Window.

Problem. Free-roam journey knowledge spans main and combat, while several schedule tests and the headless journey verify a screen-travel implementation absent from live play.

Solution. Concentrate live journey progression and its contact handoff in a coherent module, then replace retired schedule tests with tests that cross its actual interface.

Evidence: GamePlugin installs set_destination → move_player → follow_player; CombatPlugin orders start_combat after move_player. WorldScreen, screen transitions, overlay travel, and their schedule registration are test-only. README explicitly says the legacy headless journey cannot verify free roaming.

Deletion test: deleting test-only screen travel removes obsolete complexity; it does not deepen live movement by itself. Depth comes from keeping route progression, arrival, and contact knowledge local rather than merely splitting main.rs by function size.

Adapter discipline: reuse the viewport adapters from candidate 02; no hypothetical interchangeable pathfinder seam. World geometry and combat grid movement are different domain rules, not candidates for forced unification.

  • Depth: journey invariants stay internal
  • Locality: live schedule owns progression
  • Leverage: tests exercise real journeys
  • Delete retired verification implementation

Test leverage: fixed-time journey tests cover building detours, destination replacement, keyboard movement, camera follow, and enemy approach where combat starts only on contact—not on the click. Keep image capture separate from deterministic assertions.
