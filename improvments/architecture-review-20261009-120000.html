Problem

World input, pathfinding, movement, and enemy approach are coordinated in main.rs, while old screen-transition test machinery still occupies the same file.

Solution

Concentrate movement decisions and route rules in one module; keep ECS scheduling and rendering effects outside its implementation.

  • locality: route bugs stay together
  • leverage: one behavior across callers
  • tests exercise current movement

Problem

combat.rs combines turn state, ECS input/rendering, data validation, path rules, and spell resolution; rules tests cover calculations but not the actual orchestration path.

Solution

Gather combat decisions into a deep rules module and leave Bevy systems as the adapter that reads intent and applies results.

  • locality: rules change in one place
  • leverage: one seam for tests
  • tests cover turn outcomes

Problem

The recent HUD generalization expanded state handling across interaction, synchronization, restoration, and saving; those transitions are tested mostly as isolated layout round-trips.

Solution

Keep the lifecycle of each HUD window in one module, with file and ECS adapters translating its state to storage and presentation.

  • locality: visibility stays coherent
  • leverage: fewer sync rules
  • tests cover lifecycle changes

Top recommendation

Deepen world movement

It is the clearest locality win: movement behavior is concentrated in main.rs alongside obsolete screen-transition tests, while routing already has focused rules worth keeping behind a smaller seam.
